# S3.5 Harness Productionization Decision

Status: mandatory pre-S4 decision
Task: `04-28-runtime-story-dev-task`
Created: 2026-06-23

## Decision

S3.5 is required before S4 implementation.

The required S3.5 scope is narrow:

```text
production memory-maintenance structured-output runner
  + generic harness runner port
  + deterministic fake runner parity
  + bounded failure/trace behavior
```

The required S3.5 scope is not:

```text
full universal production executor for writer / orchestrator / worker /
brainstorm
```

S4 retrieval planning may start only as documentation/research after this
decision, but S4 implementation must not start until S3.5 has either landed or
has a signed deferral record with owner, risk, and compensating tests. Current
main-brain judgement is that landing the narrow S3.5 runner slice is the safer
path.

## Why This Is Required

S3g-b correctly made the production boundary honest:

- `MemoryMaintenanceWorkerAdapter` can execute when a structured-output runner
  exists;
- normal runtime factory wires the adapter;
- no-runner production path is explicit legacy compatibility fallback;
- trace records `s3_executor_migration_complete=False`.

That is good enough for a bounded compatibility commit. It is not good enough
as the base for later phases if left unresolved.

The Node-1/module requirements define workers as harness-run modules with
structured output, tool policy, failure receipts, trace, and scheduler
governance. If S4 starts while the normal memory worker still falls back to the
legacy specialist path, future agents are likely to build retrieval and later
summary/rewrite behavior on the compatibility path rather than the target
story-agent framework.

The engineering risk is not that S4 code cannot be written. The risk is that it
would be written on the wrong execution foundation.

## S3.5 Target Shape

S3.5 should add the smallest productionization layer that makes the S3 memory
worker actually run through story-agent harness mechanics.

Target flow:

```text
WorkerExecutionService
  -> MemoryMaintenanceWorkerAdapter
  -> production MemoryMaintenanceStructuredOutputRunner
  -> generic harness structured-output runner port
  -> model gateway / fake model gateway
  -> structured output parse and adapter validation
  -> WorkerResult candidate_batch / no_op / failure
  -> existing S3 governance/apply path
```

Harness core owns:

- model gateway port;
- structured-output execution mechanics;
- bounded parse/repair budget if implemented;
- timeout/cancellation propagation;
- trace/event envelope;
- fake runner/model surfaces.

Memory worker adapter owns:

- memory-maintenance prompt;
- worker output schema;
- worker-specific no-op/failure language;
- source/base/context packet mapping;
- adapter validation into `WorkerResult`.

Product services own:

- memory domain/block rules;
- candidate validation;
- proposal routing;
- governed apply;
- maintenance lock.

## In Scope

Required:

- define a generic structured-output runner port that is not memory-specific;
- implement or adapt a production memory-maintenance runner behind
  `MemoryMaintenanceStructuredOutputRunner`;
- keep `ScriptedMemoryMaintenanceStructuredOutputRunner` or equivalent fake
  coverage for deterministic tests;
- wire `rp_runtime_factory.py` so the normal runtime can use the production
  runner when configured;
- keep explicit compatibility fallback available only as a named fallback;
- trace runner mode clearly:
  - production structured-output runner;
  - deterministic fake runner;
  - legacy compatibility fallback;
- normalize provider/parse/schema errors into worker failure results;
- prove no direct truth mutation and no proposal/apply bypass.

Recommended minimal tests:

- production runner unit test with fake model gateway returning valid candidate;
- invalid structured output becomes failure with stable reason code;
- provider error / timeout becomes failure with readable trace;
- factory wiring uses production runner when configured;
- fallback metadata remains present when runner disabled;
- existing S3g-b focused tests still pass.

Optional after deterministic tests:

- bounded DeepSeek smoke through existing project configuration, with no secret
  logging and no assertion that live-provider output replaces deterministic
  gates.

## Out Of Scope

Do not include in S3.5:

- universal rewrite of `StoryGraphRunner`;
- full writer/orchestrator/brainstorm production executor migration;
- external MCP provider support;
- generic multi-agent handoff;
- broad retrieval implementation;
- chapter-close summary;
- draft review/rewrite;
- memory domain/block policy changes;
- proposal/apply behavior changes.

## Failure Behavior Required

S3.5 runner behavior must be explicit for:

- invalid structured output;
- unsupported schema version;
- provider error;
- timeout/cancellation;
- missing context packet;
- missing source/base refs;
- stale base;
- unknown tool or disabled tool if tool calls are enabled;
- exhausted repair budget if repair is implemented.

Stale base remains deterministic scheduler/adapter state. The model must not be
asked to self-repair stale base revisions.

## S4 Entry Rule

Before S4 implementation starts, one of these must be true:

1. S3.5 narrow production runner slice has landed and passed tests/review; or
2. a deferral record exists with:
   - owner;
   - reason;
   - exact risk;
   - compensating tests;
   - how S4 will avoid building on legacy fallback;
   - target slice where the runner will be landed.

Current main-brain decision:

```text
prefer option 1: land S3.5 narrow production runner slice before S4
```
